# Event capacity (headcount_max) is enforced by a database trigger, not an RPC function

Accepting a pending `event_participants` row must guarantee that Player count (organizer + accepted rows, see `CONTEXT.md`) never exceeds an event's `headcount_max`, even when two accepts race for the same event's last spot. We enforce this with a `BEFORE UPDATE` trigger on `event_participants` that takes a `pg_advisory_xact_lock` keyed on `event_id`, recounts accepted rows, and rejects the transition (via a custom SQLSTATE the client matches on) if it would overflow capacity.

We considered making the accept operation an `accept_participant(event_id, user_id)` RPC function instead of a plain `.update()` - rejected because an RPC only protects callers that explicitly use it. This codebase already has a bug pattern of a guard added at exactly one call site (`handleDecide`'s RLS-zero-rows check) that was never propagated to three other near-identical mutations. A trigger enforces the capacity invariant on every write path to the table - the existing accept flow, a future auto-accept feature (see `PLAN.md`), or a manual fix run directly against the database - without depending on any caller remembering to opt in.

Both approaches need the same advisory lock to actually be race-safe; a check-then-update sequence without it is not safe whether it lives in a trigger or an RPC. The lock is what closes the race, not the trigger/RPC choice - that choice is only about where the enforcement lives and whether it can be bypassed by a future caller. The tradeoff: the check is invisible from application code (a reader of `handleDecide` won't see it without knowing to look in `supabase/migrations/`), and its errors surface as raw Postgres exceptions rather than a typed function result.
