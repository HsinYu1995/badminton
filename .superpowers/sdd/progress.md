## Manual on-device verification (Android emulator) - findings
- Hit "This site can't be reached, 127.0.0.1 refused to connect" after approving on Google's consent screen: Google's post-consent redirect targets `http://127.0.0.1:54321/auth/v1/callback` (the URI registered in Google Cloud Console, matching Supabase's default-derived callback), but `127.0.0.1` inside the Android emulator refers to the emulator itself, not the host machine running Supabase.
- First fix attempt (commit 69c1383, since reverted): pointed `[auth.external.google].redirect_uri` at `http://10.0.2.2:54321/auth/v1/callback` (the emulator's host-loopback alias) and asked the human to register that as an additional Authorized redirect URI in Google Cloud Console. This failed with "invalid request" on Google's own page, before the account picker even loaded: Google rejects non-HTTPS redirect URIs for Web application OAuth clients unless they target a real loopback address (`127.0.0.1`/`localhost`) - `10.0.2.2` doesn't qualify even though it's functionally a loopback alias from the emulator's perspective.
- Correct fix (commit cd5cbac): reverted `redirect_uri` back to empty (defaults to `127.0.0.1:54321`, already registered with Google, no Console changes needed) and instead ran `adb reverse tcp:54321 tcp:54321` to forward the emulator's own `127.0.0.1:54321` to the host machine. This is the standard fix for Android-emulator + OAuth-loopback-redirect situations. Verified: Supabase restarted cleanly, `google:true` still reported, `adb reverse --list` confirms the forward is active.
- **Confirmed still broken** after the `adb reverse tcp:54321 tcp:54321` fix above: end-to-end click-through consistently landed on `http://127.0.0.1:3000/#access_token=...` (the default `site_url`) instead of back in the app, both from the real app and from manually driving `/auth/v1/authorize` in Chrome. `127.0.0.1:3000` isn't served by anything, so the browser showed "site can't be reached" with the tokens stranded in the URL fragment - the app's `WebBrowser.openAuthSessionAsync` never saw its own `exp://` redirect and so never completed.
- **Root cause (found by reading GoTrue's source, `supabase/auth` `internal/utilities/request.go`, `IsRedirectURLValid`):** when a `redirect_to` URL's host parses as a literal IP address (`net.ParseIP` succeeds), the function returns `ip.IsLoopback()` immediately and never falls through to check `additional_redirect_urls` at all - so no allow-list entry, glob or exact, can ever make it accept a non-loopback IP host. Expo Go's `makeRedirectUri()` defaults to the Metro dev server's LAN address (`exp://10.0.0.194:8081` in this environment), which is exactly such a non-loopback IP-literal host, so GoTrue silently discarded it and fell back to `site_url` on every attempt. This is unrelated to (and was not fixed by) the Supabase-connectivity `adb reverse`/`redirect_uri` fix above - that fix made the *initial* `/authorize` call reachable; this bug breaks the *final* redirect back into the app. Tried and ruled out: adding the exact literal `exp://10.0.0.194:8081` to `additional_redirect_urls` - had no effect, confirming the allow-list is genuinely never consulted for this host.
- **Real fix:** run Metro bound to the IPv4 loopback instead of the LAN, so `makeRedirectUri()` resolves to `exp://127.0.0.1:8081` - a loopback host, which `IsRedirectURLValid` always accepts regardless of the allow-list. `expo start --localhost` alone was not sufficient on this Windows machine: Node resolved `localhost` to the IPv6 loopback (`[::1]`) first, and `adb reverse` only forwards to the host's IPv4 loopback, producing a silent `ERR_EMPTY_RESPONSE`/connection-refused instead of reaching Metro. Forcing IPv4-first DNS resolution (`NODE_OPTIONS=--dns-result-order=ipv4first`) fixed that. Added `npm run android:emulator` (`scripts/start-android-emulator.js`) so this isn't tribal knowledge, and reverted the now-unneeded literal allow-list entry in `supabase/config.toml` (documented the real constraint there instead). Also requires `adb reverse tcp:8081 tcp:8081` per emulator boot, alongside the existing `tcp:54321` forward.
- **Verified end-to-end, twice**, including once on a fully fresh emulator boot (`-no-snapshot-load`) with the corrected config: tapped "Sign in with Google" in the running app, completed the real Google OAuth round-trip, landed back on the authenticated Discover/tab UI, and successfully signed out - all confirmed against GoTrue's own audit log (`/authorize` → `/callback` → `/user` 200 → later `/logout` 204, real account `maplestoryya18@gmail.com`). The Google sign-in plan is now fully complete with no outstanding manual step.
